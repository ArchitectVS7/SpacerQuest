# 0.5.2 Spec Consistency Review

**Status:** REVIEW (T-102, 2026-07-30). **This is a cross-check, not a re-analysis.** It reads
`docs/EXPLORE_REDESIGN.md` (T-100) and `docs/HANGOUT_REDESIGN.md` (T-101) against THE THREE
DESIGN RULINGS in `TASKS.md` and against each other. It re-derives no design, re-opens no
ruling, and adds no new one.

**Where this doc and a spec disagree, THIS DOC GOVERNS**, and the correction is carried as a
numbered directive to the named downstream task (§3). Neither spec was edited by this task;
T-102 changed no engine, content, sim or UI source file, and created exactly this one file.

| the three interaction questions are **the spec's job** | §3.3 answers (a) travel-away → forfeit by location predicate, (b) death → forfeit at succession, (c) second recovery → the verb is refused with no die and no fuel, **and a fourth** (d) the day-30 marker → survives untouched. Nothing quietly substituted. The one thing worth naming positively: the spec answered a
**fourth** question (the day-30 era flip) that T-100's own task body demanded but the ruling's

### 1.2 Ruling 2 — "the die effect uses the EXISTING, SHIPPED-EMPTY hook" → **HONOURED**

> *"'+y on a roll' is expressed as a floor / extra die / reroll. NO new check-level modifier
> surface is to be built. If a content row provably cannot be expressed this way, that is a
> finding to REPORT, and adding the second surface is a fresh owner call."*

| Ruled clause | Where | Evidence |
| --- | --- | --- |
| expressed as **floor / extra-die / reroll**, nothing else | §4.2 — exactly three worked items, one per kind, ordered by power, each with its accumulator interaction (floors MAX, rerolls SUM, extra dice SUM-then-CLAMP) | §4.2 |
| **no new check-level modifier surface** | §4.3 L4: *"`check()`'s signature (`dice.ts:137`) is untouched by everything in this document"*; *"Building the scoping surface is a fresh owner call… and this spec does not propose it"* | Verified: `packages/engine/src/dice.ts:137` reads `export function check(die: number, statValue: number, dc: number): CheckResult` — the spec proposes no change to it |
| a row that **cannot** be expressed is a **finding to REPORT** | §6 Finding F-100-1, with the full per-instance cost enumerated and a rejected alternative | §6 |

**The one call this task exists to force, adjudicated.** F-100-1's *recommended resolution*
gives `equipmentDiceBenefits` a **second loop** over a second content table
(`EXPLORE_MODULE_DICE_BENEFITS`). That sits against the hook's own header comment, verified
verbatim at `packages/engine/src/dice.ts:40–42`:

> *"A future die-granting module is one entry in the content table; **nothing here or at any
> call site changes**."*

**This is NOT a departure, and here is the decision rule.** Ruling 2's operative prohibition is
on a *second check-level modifier surface* — a fourth way to express "+y on a roll" beyond the
three `DiceBenefit` kinds. The spec builds none:

- three kinds only, the shipped union (`packages/content/src/crew.ts:52`);
- the same `applyBenefit` fold and the same clamps (§6: *"Zero new accumulator"*);
- the same three call sites, unchanged (§6: *"Zero call-site changes"*);
- `check()` untouched (verified above).

The second loop adds an **id-namespace carrier**, not a modifier kind — it exists solely
because `EQUIPMENT_DICE_BENEFITS` is keyed by `SpecialEquipmentContentId`, which is derived
from the *shipyard's purchasable table*, so a key cannot be obtained without also putting a
unique derelict find on every yard shelf. The crew-parity proof survives because the `table`
parameter is already injectable — verified at `packages/engine/src/dice.ts:52–56`,
`equipmentDiceBenefits(ship, table = EQUIPMENT_DICE_BENEFITS)`.

**Recorded as a precondition, not a blessing** — see directive **D2**. A comment that
contradicts the code it heads is exactly the failure class `EXPLORE_REDESIGN.md` §3.3(d) itself
flags for the subsistence floor, and T-112 must not leave one behind.

### 1.4 Examined and cleared — five near-misses, each with why it is NOT a departure

These are the five places a careless reading would call a substitution. Each is recorded with
its clearing argument so a later reader does not re-litigate it.

1. **`recoveryDays: 0` for bands 0–1, i.e. 58% of successful boards resolve same-day**
   (`EXPLORE` §3.2, §5.2). *Not a departure.* Ruling 1's rejected alternative was a same-day
   scaling **die** cost; §3.5 forbids charging a die per recovery day outright. N = 0 at the
   bottom of the ladder is "N scaling with the outcome's power" at its floor, and the spec
   gives the reachability reason (the median day-120 captain carries 27 fuel, p25 = 4).

2. **`'venue-not-offered'` and `rankClientele` are new ENGINE behaviour** (`HANGOUT` §2.6,
   §3.1 rows 23 and 25). *Not a departure.* Ruling 3 excludes *per-port house rules needing an
   engine special case*. Both are single rules evaluated identically at every port — the spec
   says so explicitly of the refusal (*"a new kind of refusal — one rule, evaluated the same
   way at every port — not a per-port branch"*) — and both are placed engine-side by §3.1.

3. **Ruling 3 says "the six venues"; `HangoutVenueId` has seven.** *Not a departure — the
   ruling's count is loose prose.* The spec mirrors the shipped `PlayerAction` union verbatim;
   verified at `packages/engine/src/types.ts:1112`:
   `venue: 'dare' | 'meet' | 'befriend' | 'insult' | 'rumor' | 'borrow' | 'repay'`. TASKS.md's
   own T-101 body describes the same seven strings as *"six venues: `dare`, `befriend`,
   `insult`, `meet`, `rumor`, plus `borrow`/`repay`"* — the ruling inherited that phrasing, not
   a scope line.

4. **Per-port control over `borrow`/`repay` membership** (`HANGOUT` §2.2 ruling 5). *Not a
   departure.* Band, rate, term and `LENDER_ID` stay global — `LENDER_ID = 'npc-penny-wise'`
   verified at `packages/content/src/lending.ts:56` — and content gets exactly one bit: desk
   present or absent. The *ledger* stays engine-side (§3.1 row 19), which is what ruling 3
   reserved. A per-port band would have been a second lender, i.e. a new rule; the spec rejects
   exactly that.

5. **`EXPLORE` §2.4 keeps TWO draw models alive across T-110 → T-113.** *Not a departure from
   any ruling* — it is the extraction discipline the standing constraint demands, written down
   because T-110's "byte-identical goldens" acceptance and its "outcome is a content-supplied
   payload" acceptance would otherwise be in direct conflict and the coder would have to guess
   which to break. Noted approvingly and carried forward as directive **D1**.

## §2 · Collision

### 2.1 The save bump — **THE RECOMMENDATION**

> **ONE bump for the whole 0.5.2 track. `CURRENT_SAVE_VERSION` 12 → 13, taken by T-111, with
> `MIGRATIONS[12]` backfilling `player.recovery = null` and the matching `deserializeState`
> `??= null`. The Hangout milestone takes NONE.**
>
> **Landing order: M2 in full before M3.** This is already forced by TASKS.md's `after:` chain
> (T-120 · `after: T-116`). Preserve it. Under this order the second milestone cannot
> invalidate the first's migration, **because the second adds no persisted shape at all.**

Both specs independently arrive here (`EXPLORE` §3.4's flag to T-102; `HANGOUT` §4.4 and §8
item 1), and this review confirms rather than merely accepts the Hangout half:

- **Verified ground for "the Hangout owes none":** the new `'venue-not-offered'` value lands on
  `HangoutEvent.failReason` / `LoanEvent.failReason`, and `HangoutEvent`'s own header at
  `packages/engine/src/types.ts:591–592` reads *"This is an `eventLog` entry, not a GameState
  field — no save migration, but it carries a schema variant + drift guard (schema.ts)."* No
  `GameState` field is added anywhere in `HANGOUT_REDESIGN.md`.
- **The one residual, named so it is not mistaken for a bump.** Widening a serialized union
  adds a value old saves cannot contain (additive-forward, no migration owed), but a v13 save
  containing the new value cannot be read by a pre-T-120 build. That is the normal
  forward-compat property of every event addition in the file, not a new risk, and it does not
  change the recommendation.

**Contingency, stated so nobody improvises one.** If any M3 task discovers it needs a
`GameState` field after all — nothing in `HANGOUT_REDESIGN.md` does — it takes **13 → 14** with
its own `MIGRATIONS[13]` and **never retro-edits `MIGRATIONS[12]`**.

### 2.2 The second-order save question both specs left open — closed here

Neither spec answers this, and it is the collision that would actually bite:
**`EXPLORE` §6 F-100-1 has T-112 add three `ShipState` booleans, and T-112 runs *after* T-111
has already consumed the bump.** The spec asserts they *"ride §3d's save bump"*, but
`MIGRATIONS[12]` backfills only `player.recovery`.

Verified precedent that resolves it without a second bump — the seven existing module flags are
**optional** in the schema and backfilled in the loader, not migrated:

- `packages/engine/src/schema.ts:261–267` — `hasTransWarpDrive`, `hasCloaker`, `hasAutoRepair`,
  `hasStarBuster`, `hasArchAngel`, `isAstraxialHull`, `hasTitaniumHull`, each
  `z.boolean().optional()`;
- `packages/engine/src/state.ts:227–233` — all seven backfilled `??= false` in
  `deserializeState`.

Directive **D3** carries the resolution.

### 2.3 The day loop — both systems touch it; they do not contend

| | Explore (M2) | Hangout (M3) |
| --- | --- | --- |
| What it adds to `endDay` | ONE block: tick/payout/forfeit | **Nothing** |
| Position | pinned immediately AFTER the T-1307 port-income block and immediately BEFORE the T-1604b subsistence floor (`EXPLORE` §3.3(d)) | n/a |
| Guard | `recovery !== null`, and **rng-free** (pure arithmetic + a compare) | n/a |
| Day-phase surface | the fifth `ExplorationFailed` refusal | uses the EXISTING `hasHangout` gate, verified at `packages/engine/src/day.ts:382–393` |

**Verified: the position Explore claims is available and the reason it gives is real.** The
subsistence floor's own comment at `packages/engine/src/day.ts:1039–1043` asserts *"The T-1307
port income immediately above is the LAST credit mutation of the dusk… so this is a true
END-of-dusk floor."* A recovery payout is a credit mutation, so it must land above the floor or
that invariant becomes false — which is why `EXPLORE` §3.3(d) obliges T-111 to update that
comment **in the same commit**. Directive **D4** restates it, because it is the single easiest
thing in this track to forget.

**The Hangout's day-loop effect is FREQUENCY, not position.** T-121 makes borrowing legal at 14
ports instead of 1, so the existing dusk interest accrual → subsistence floor → recovery payout
ordering simply runs on far more days. That is a **measurement note for T-125**, never a reason
to move the floor or the recovery block. Directive **D5**.

## §4 · What this review deliberately did not do

- **It did not re-analyse either system.** Both specs' designs are taken as given; only their
  fidelity to the rulings and their mutual consistency were examined.
- **It did not edit either spec.** Corrections are directives (§3), so the specs remain the
  record of what T-100 and T-101 delivered and this doc remains the record of what T-102 found.
- **It did not open a new design question.** N2's `valueBandFor` and D7's rename are naming, not
  design.
- **It did not touch source.** No engine, content, sim or UI file was modified.
